## Prioritized backlog (P0 → P4)

This app has real, active users and real money moving through Mercado Pago today. Priority below is ordered by risk to users/money/data in the app's _current_ state, not by feature desirability. Each item's full detail (files, exact gaps, what's already done) is in the "Needs decisions" list further down this doc, or in the doc noted.

### P0 — active risk right now, not a future concern

1. **Every Vercel preview deployment hits the production Neon database.** Confirmed (2026-08-19, re-confirmed unchanged 2026-09-04): only one Neon branch/compute exists for this project (`br-proud-dream-af3s8vw7`, the default) — no separate staging/preview database. Any PR's preview deployment reads and writes real production data; a bad migration or seed script in a preview build can corrupt live data with zero isolation. Fix is well-understood (Neon supports branch-per-PR / a dedicated preview branch) — this is a live-risk item blocked on doing the work, not on a business decision. See "Confirm a staging/preview environment" below.
2. ~~**No rate limiting, CSRF-specific review, or CAPTCHA anywhere in the app.**~~ Done (2026-09-06): Vercel WAF rate limiting (`@vercel/firewall`) + Vercel BotID on `/api/onboarding`, `/api/player/reservations`, `/api/player/waitlist` (POST), and rate limiting alone on `GET /api/player/clubs` (browse/scraping target). CSRF reviewed separately — no real gap found (Clerk's `SameSite=Lax` session cookie + zero Server Actions + double auth-gated mutating routes already block the classic attack; no code change needed). See [SECURITY.md](SECURITY.md) for full detail on both.

### P1 — real legal/compliance exposure with live users, or blind spots in a live system

1. **Terms of Service & Privacy Policy still have no real content.** Blocked on attorney review, not an engineering task — see [COMPLIANCE.md](COMPLIANCE.md) for the drafted-but-unreviewed clause language and the full gap list (AAIP registration, cross-border-transfer consent, DPAs). `/terms` and `/privacy` still 404.
2. **Real legal invoicing (facturación electrónica via ARCA/ex-AFIP)** — whether this is actually legally required for this business needs a business-side/accounting answer, not a code decision; the current PDF receipt (`lib/pdf/ReceiptDocument/`) is explicitly not a legal invoice. Don't start any implementation planning here before that answer exists.
3. **No crash-reporting/error-monitoring service** (e.g. Sentry) — the app has zero visibility into production errors right now. Low effort to add once a provider is chosen; the only blocker is that choice + an account/DSN.

### P2 — cheap fixes and decisions with real but lower urgency

1. **Multi-language UI (Spanish).** Elevated from where the prior backlog pass flatly listed this: `app/layout.tsx` hardcodes `lang="en"` and every UI string is English, while every business signal in the codebase points to an Argentine, Spanish-speaking user base — ARS-only pricing, Mercado Pago as the sole payment processor (`initMercadoPago(publicKey, { locale: "es-AR" })`), CUIT-formatted tax IDs, and the club timezone silently defaulted to Buenos Aires everywhere. This is inference, not a confirmed business fact (no explicit "target market: Argentina" statement exists anywhere in the repo) — but the inference is strong enough that an English-only UI for what looks like a Spanish-speaking real user base is a real product gap today, not a someday-nicety.
2. ~~**Footer contact email/phone**~~ — done (2026-09-06), see [PROJECT_STATUS.md](PROJECT_STATUS.md). No social links exist in the app at all (a prior version of this doc incorrectly implied placeholder social links existed).
3. **GA4/Google Search Console setup + sitemap submission** — needs account access, not something doable from the repo.
4. **Neon PITR retention is only 6 hours** (`history_retention_seconds: 21600`) — fine for same-day recovery, but anything older is unrecoverable. Worth revisiting if a longer window matters as the business grows; not urgent today but cheap to change (a Neon plan/config setting).

### P3 — feature/design decisions with no urgency signal found

1. Recurring/repeating reservations — needs a decision on conflict handling for a recurring slot colliding with something later.
2. Split payment among the group booking together — needs a real payment-split design (Mercado Pago multi-payer vs. manual settlement).
3. Ratings/reviews for clubs/courts — needs a moderation policy before opening to the public.
4. Referral program / loyalty points — needs a full program design (rewards, fraud prevention).
5. Calendar sync (.ics / Google Calendar) — needs a decision on one-way export vs. two-way sync.
6. Real-time availability (WebSocket/SSE vs. tuned polling) — currently 15s polling via React Query on both Browse Courts and the owner Reservations view; no evidence in the repo of this actually causing a known problem (no complaint, no TODO, no incident note found) — this is a theoretical optimization, not a fix for an observed issue.
7. Player search/discovery, favorites/"book again", owner-side analytics beyond the current dashboard — each needs its own small scope decision, otherwise low effort.
8. Customizable receipts (owner-editable fields on the existing PDF template) — a smaller, separate ask from the legal-invoicing item above (P1); needs a decision on exactly which fields are owner-editable.

### P4 — exploratory / no evidence anyone has asked for this

1. Player social features: in-app chat — no schema exists at all; a full feature build, not a backlog item to "pick up." Tournaments/matches/rankings and performance summary are no longer in this list — see below, done. Doubles partner history / latest-partner card is also no longer in this list — see below, done.
2. PWA/offline support — needs a decision on whether offline functionality even makes sense for a live-availability booking app; no evidence anyone has requested it.
3. Mobile app / push notifications — a big scope decision (native vs. wrapped web, notification infra choice), no urgency signal.
4. QR check-in per reservation, `react-joyride` onboarding tour, `@dnd-kit` drag-to-reorder courts — each needs a product decision before any implementation planning; the latter two had their now-unused packages already removed (2026-08-19) and would need reinstalling if scoped.

**Deviations from the suggested priority framework:** real-time availability was placed at P3 rather than a higher tier since 15s polling has no documented complaint or incident behind it (the framework explicitly allows this check). Multi-language was moved from a flat, unprioritized listing up to P2 given concrete evidence (ARS/Mercado Pago/es-AR locale/CUIT) of an Argentine user base, though that market is still an inference, not a confirmed fact — flagged as such above. Legal invoicing and ToS/Privacy are both P1 because they're live legal exposure, but both are explicitly gated on a non-engineering answer (attorney review, business/accounting decision) rather than something this backlog can resolve by itself.
