# Play Padel — Project Status

_Last updated: 2026-09-04_

A padel-club booking platform: players browse clubs/courts and book time slots; club owners manage their courts, availability, and reservations.

Convention used below: a feature described in plain text is fully wired to a real Prisma-backed API. Where a `(mocked: ...)` note is present, that feature's data is hardcoded/placeholder and needs real backend work before it's production-ready.

Related docs: [ARCHITECTURE.md](ARCHITECTURE.md) (stack, diagrams, folder structure), [API.md](API.md) (full route list), [DATABASE.md](DATABASE.md) (Prisma models + ERD), [ROADMAP.md](ROADMAP.md) (what's next), [SECURITY.md](SECURITY.md).

Tournaments/matches, doubles partners, and player style/handedness all now have real Prisma models — every Player Overview feature below is real, no mocked data remains in that section.

## Auth & Onboarding

- Login / signup — Clerk's `<SignIn>`/`<SignUp>` components, redirect to `/dashboard` (login) or `/onboarding` (signup after account creation).
- SSO callback — Clerk's `<AuthenticateWithRedirectCallback>`.
- Onboarding wizard — multi-step form branching on player vs. owner, submits to `/api/onboarding`. Player path upserts `UserProfile`; owner path creates a real `Club` row then upserts `UserProfile` with `role: "owner"`. Continue/Submit are disabled until the current step's own required fields are actually valid (checked via an independent zod parse, not RHF's own error state, so nothing flashes red before the user has touched a field).
  - **Player flow**: Profile (name, email, phone, gender) → Location (address, country/province/city cascading picker, zip code) → Padel style (category, preferred side, dominant hand) → Terms.
  - **Owner flow**: Club Basics (name, email, phone, address, country/province/city, zip code) → Legal & Billing (legal name, CUIT-formatted tax ID) → Operating Hours → Profile (display name + full review summary) → Terms. The Plan step has been **removed entirely** (2026-09-04) — `PlanStep`, `PlanPricingCard`, and their `consts`/`types`/`utils` were deleted from `app/onboarding/_components/OnboardingWizard/components/steps/PlanStep/`, and `app/onboarding/types.ts`/`OnboardingWizard.tsx` no longer carry a plan field. Plan selection now happens later, post-onboarding, via `components/PlanSelectionModal/` (see the new "Club membership / billing" section below).
  - Google OAuth auto-fill — name, email, and avatar (`photoURL`) are pulled from Clerk's normalized user data (populated from Google's `given_name`/`family_name`/profile photo on sign-up) and pre-fill the relevant fields; still fully editable.
  - Cross-field auto-fill chains — club `legalName` and the owner's `displayName` track the club `name` live until manually overridden; `country` is auto-detected from the phone field's calling code.
  - Phone field — a compound field with a searchable calling-code combobox (real flag icons via `country-flag-icons`, not emoji) next to a plain number input. Selecting a code sets `country` directly; the number itself is formatted live to the **selected country's own real national convention** via `libphonenumber-js`'s `AsYouType` (not a single hardcoded format), with a matching per-country example placeholder.
  - Location — real cascading Country → Province/State → City picker (`country-state-city` npm data, no external API), shared between both flows via one `useCountryProvinceCityFields` hook so the parent step can lay the fields out however it needs.
  - Operating Hours step (owner flow only) — a real weekly availability template collected during onboarding (`app/onboarding/_components/OnboardingWizard/components/steps/OperatingHoursStep/`, with a `QuickSetupPanel` to fill every day at once), persisted to the new `Club` operating-hours columns (migration `20260902031149_add_club_operating_hours`) and reused later by `resolveDefaultCourtAvailability` when a court is created with no explicit availability of its own.
  - Plan selection has moved out of onboarding entirely — see the note above; `Club.plan` is now set later via `components/PlanSelectionModal/`, not during signup.
  - Terms & conditions checkbox — enforced at submit time, and persisted for real: `acceptedTermsAt DateTime?` on `UserProfile`, stamped with `new Date()` by `app/api/onboarding/route.ts` on both the player and owner upserts (create and update paths), since both onboarding flows already require `confirmedAge`/`acceptedTerms` to be `true` via Zod validation before the handler runs.
- Invite-error page — static error message, shown when profile provisioning fails; no logic of its own.

## Player Dashboard (`/dashboard`, role: player)

**Bento cards (Hero, Skill Overview, Session Load, Progress & Goals, Schedule)** — all fully real, computed from the player's actual reservation history via `useMyReservations()`.

**Player Overview sidebar/banner**:

- Player style card (preferred side + dominant-hand badge) — real, editable data. `preferredSide`/`dominantHand` are nullable `UserProfile` columns, now also collected upfront in the onboarding wizard's Padel style step; a pencil icon still opens `EditPlayerStyleDialog` to change them later via `PATCH /api/me`, and unset values render "Not set yet". Served through `usePlayerOverviewData()` (`PlayerOverview/hooks.ts`) reading `useAuth().user`.
- ~~Latest partner card~~ — done (2026-09-06). Real, via a new `ReservationPartner` join table (migration `20260906120000_add_reservation_partners`): a reservation's booker can optionally tag up to 3 other registered players as co-players at booking time (no confirmation needed from them). `GET /api/player/latest-partner` derives the current player's most recent shared reservation and "times played together" count (`core/reservations/services/reservationPartners.service.ts`); `PlayerOverview/hooks.ts`'s `useLatestPartner()` feeds `LatestPartnerCard`, which renders an empty state when the player has no partner history yet. Clicking a real partner still opens the shared `PlayerProfileCard`, now populated with their real profile data — its win-rate fields stay empty (no Match/Tournament model exists), matching that component's pre-existing optional-field convention.
- ~~Performance summary~~ — done. Real, via the full Tournaments feature (`Tournament`/`TournamentCategory`/`TournamentTeam`/`TournamentGroup`/`TournamentMatch`/`MatchSet` models): `GET /api/tournaments/performance-summary` calls `computePerformanceSummaryForPlayer` (`core/tournaments/services/standings.service.ts`), which counts the player's distinct tournaments played/won and derives their last 5 decided (COMPLETED/WALKOVER) match results across any of their tournaments. `PlayerOverview/hooks.ts`'s `usePerformanceSummary()` feeds `PerformanceSummarySection`, unchanged since it already consumed this exact shape; a player with zero tournament teams gets a zero-value summary (`0/0`, no latest results) rather than a hidden section.

**Players directory** (`/dashboard/players`) — fully real: a public, searchable (client-side, by name) list of every active player, backed by `GET /api/players`. Each row opens the same `PlayerProfileCard` used by the Latest Partner card, populated from real `UserProfile` data.

**Browse Courts** (`/dashboard/browse`) — fully real: club picker, per-court availability grid (15s live poll), and the book-slot flow all hit real Prisma-backed endpoints with server-side conflict checks. If the club has `requiresPrepayment` set, booking a slot creates a 15-minute `SCHEDULED` hold and redirects to a real Mercado Pago Checkout Pro session instead of confirming instantly; `BookingConfirmDialog` branches its copy/button label accordingly. A slot inside an active court closure renders distinctly (dashed border, non-clickable) with its reason shown on hover, and booking it is also rejected server-side. `/dashboard/browse/payment-return` polls the player's own reservation list to show a processing/success/failed state after returning from checkout.

**My Reservations** (`/dashboard/my-reservations`) — fully real: reservation list and self-cancel flow (2-hour cutoff enforced server-side).

## Owner Dashboard (`/dashboard`, role: owner)

Everything here is fully real — no mocked data found on the owner side.

- **Courts** (`/dashboard/courts`) — court list/table, create/edit form, deactivate (soft delete), weekly availability editor, and a "Closures" action per court that opens a drawer to block the court for a date/time range with a required reason (shown to players); lists past/upcoming closures with cancel actions, and an "apply to all courts" checkbox loops the create call across every active court. Creating a closure is blocked (409) if it overlaps active reservations. All backed by `/api/clubs/courts*`.
  - **Court create/edit form fields** — name, surface, indoor toggle, color, photo, slot duration, a "Price (per reservation)" field (used when the club requires prepayment), and (new, migration `20260902205935_add_court_physical_characteristics`) real **physical characteristics**: `wallType` (`WallTypeField`) and `netType` (`NetTypeField`) as free-text/select fields, plus a `lighting` boolean toggle — all in `CourtFormSheet`, persisted on `Court`.
  - **Bulk edit across courts** — `BulkEditCourtsSheet` (`app/dashboard/courts/_components/CourtsView/components/BulkEditCourtsSheet/`) lets an owner select multiple courts and apply a shared field change (e.g. price, availability) to all of them in one action, backed by tests in `BulkEditCourtsSheet.test.tsx`.
  - **Weekly availability / operating hours can now cross midnight** — e.g. open 09:00, close 02:00 the next day. `core/courts/schemas/court.schema.ts`'s time-range validation only rejects `startTime === endTime`, not `endTime < startTime`; `core/courts/services/courts.service.ts` added a `resolveWindowEnd` helper (used by both `getCourtSlots` and `getClubsAvailability`) that rolls the end time to the next calendar day when it's earlier than the start time. The old "end time must be after start time" UI-only validation was removed from both the owner-side availability editor and the onboarding Operating Hours step.
- **Reservations** (`/dashboard/reservations`) — availability grid, reservations table, slot details dialog, and Complete/No-show/Cancel actions (owner-cancel refunds any `COMPLETED` payment via Mercado Pago first). All backed by `/api/clubs/reservations*`.
- **Club Settings** (`/dashboard/settings/club`) — club profile form (name, legal name, tax ID, contact, a "Require online payment at booking" toggle for `requiresPrepayment`), 1:1 with the `Club` model. Timezone/currency are no longer user-facing anywhere in the app — every club is implicitly Buenos Aires time / ARS, silently defaulted. `ClubSettingsTabs` (`app/dashboard/settings/club/_components/ClubSettingsTabs/`) now has multiple tabs, including:
  - **Operating Hours tab** — `OperatingHoursSettingsCard`, a club-wide weekly availability template (the "no club-wide operating hours concept" gap from the previous version of this doc is closed; migration `20260902031149_add_club_operating_hours` added the backing columns). This club-wide template is used as the default when creating a new court with no explicit availability of its own; it does not retroactively change existing courts' own schedules.
  - **Payout method tab(s)** — a club now needs _either_ a connected Mercado Pago account _or_ a configured bank-transfer account to be considered "operational" (see the Club Operational Gate section below). `BankTransferAccountSettingsCard` (new, migration `20260904030017_add_club_bank_transfer_account`) lets an owner enter bank account details as an alternative payout method to Mercado Pago, backed by `core/clubs/services/bankTransferAccount.service.ts` and `POST/GET /api/clubs/bank-transfer-account`.
- **Dashboard Home owner cards** (Hero, Schedule, Utilization, Overview, Activity) — all computed from a shared `useOwnerReservationSummary()` hook hitting real reservation data.
- **Audit Log** (`/dashboard/audit-logs`) — fully real: filterable (entity, action), paginated table over `GET /api/clubs/audit-logs`.
- **Club Operational Gate** (`app/dashboard/_components/ClubOperationalGate/`) — wraps the entire owner dashboard; while `useClubOperationalStatus()` is loading, shows a `BouncingBall` spinner (see the loader-rollout note below) rather than either the real dashboard or a gate screen, to avoid flashing the wrong state. A non-operational club never mounts `children` at all. Two causes, computed server-side by `getClubOperationalStatus()` (`lib/mercadopago/operationalStatus.ts`), precedence `MP_NOT_CONNECTED` > `CLUB_INACTIVE`:
  - `MP_NOT_CONNECTED` — the club has **no payout method at all**: neither a `CONNECTED` Mercado Pago account nor a configured bank-transfer account. Despite the name, this cause now covers "no payout method", not just "no MP" — renders `PaymentActivationScreen`, which (as of this session) also surfaces the bank-transfer option as an alternative to connecting Mercado Pago (dual gate), via a step indicator (`ActivationStepIndicator`).
  - `CLUB_INACTIVE` — `Club.status !== "ACTIVE"` (checked only once a payout method exists) — renders `ClubInactiveCard`.
  - `MercadoPagoConnectedDialog` (new) shows a one-time confirmation dialog after a successful MP OAuth connect redirect (`?mpConnect=success`), consumed and stripped from the URL on mount by `DashboardShell`.
- **Club status admin control** (`/admin/club-status`, `app/api/admin/club-status/route.ts`) — corrected (2026-09-06): no longer a hand-typed-secret tool. `app/admin/layout.tsx` now gates every page under `/admin/*` with a real Clerk-based admin check (`isAdminUser()`, `lib/auth/admin.ts`) — a non-admin gets a plain 404, and every mutating call on the page rides the caller's own same-origin Clerk session cookie. `MEMBERSHIP_ADMIN_SECRET` is dead — no longer referenced anywhere in app code. Lets an operator look up a club by id and change its `status` (`ACTIVE`/`INACTIVE`/`SUSPENDED`/`DISABLED`), recording `updatedBy`/`updatedAt`. Also hosts the hidden **FREE plan activation** control — see "Club membership / billing" below.
- **Club membership reactivation** — `POST /api/clubs/membership/reactivate` (`app/api/clubs/membership/reactivate/route.ts`) lets an owner resume a previously-cancelled/lapsed Mercado Pago preapproval-based membership; surfaced in the dashboard via `ClubInactiveCard`.
- **Club membership / billing (post-onboarding plan selection)** — real, via `components/PlanSelectionModal/` and `core/billing/services/membership.service.ts`, using Mercado Pago **preapprovals** (recurring subscriptions) rather than one-off Checkout Pro payments:
  - Four real, purchasable tiers (`BASIC`/`PRO`/`PLUS`/`MAX`) with ARS pricing and a monthly/annual toggle (`lib/consts/planPricing.ts`, `PLAN_ORDER`).
  - Checkout collects the club's payer identification (DNI/CUIT type + number) via `CardTokenForm` wrapping Mercado Pago's `CardPayment` Brick (`@mercadopago/sdk-react`) — raw card data never touches app servers/state. `core/billing/schemas/membershipCheckout.schema.ts` validates the identification payload; `MembershipCheckoutDrawer` and `PlanSelectionModal` prefill it from a previously-saved payer identification and offer a "save for future" option so a returning owner doesn't have to re-enter it on plan changes/renewals.
  - A hidden, **admin-only "FREE" plan tier** exists (`activateFreePlan` in `core/billing/services/membership.service.ts`, `POST /api/admin/membership-free-plan`, wired into the `/admin/club-status` admin page) — deliberately **excluded from `PLAN_ORDER`** so no real customer can ever select or see it in the normal plan-selection UI; it exists purely to unblock one club's dashboard for internal testing without a real Mercado Pago charge.

## Backend domains (`core/`)

- `clubs`, `courts`, `reservations`, `users`, `audit` — real Prisma-backed services, all reachable from `app/api` routes, all exercised by real mutations or the UI described above. `logAudit()` is called from every real owner/player mutation: reservations (created/cancelled/completed/no_show), courts (created/updated/deactivated), court closures (created/cancelled), club (created at owner onboarding, updated via Club Settings), and player onboarding (created). `AuditLog.clubId` is nullable to allow club-less events like player-profile creation. `GET /api/clubs/audit-logs` and the `/dashboard/audit-logs` page let an owner view their club's trail with filters and pagination.
- `billing` — invoice/payment logic (create/issue/void invoices, record payments, refunds, cash summaries) is implemented against real `Invoice`/`Payment` models, and is now reachable from the HTTP layer: `POST /api/player/reservations` creates and issues an invoice when a club requires prepayment, and `POST /api/webhooks/mercadopago` records the resulting `DIGITAL` payment (and logs a `"payment.confirmed"` audit event) or voids the invoice, depending on the payment outcome. Real Mercado Pago integration lives in `lib/mercadopago/` (`client.ts`, `preferences.ts`, `payments.ts`, `webhookSignature.ts`, `refunds.ts`) — thin wrappers around the `mercadopago` npm SDK. Both self-cancel and owner-cancel now refund any `COMPLETED` payment via Mercado Pago before cancelling; a refund failure blocks the cancellation instead of silently proceeding.
- `notifications` — persisting `Notification` rows and actual email delivery (via Resend) work for all three flows now: reservation cancellation, invoice paid, and reservation reminders. `GET /api/cron/notifications` (Vercel Cron, daily at 08:00, see `vercel.json`) calls `getPendingReservationReminders()` and dispatches a `RESERVATION_REMINDER` email per pending reservation; dedup (no more than one reminder per user per calendar day) is handled inside that function. The route isn't Clerk-authenticated (Cron has no session) — it checks its own `CRON_SECRET` bearer token instead, and `proxy.ts` allowlists `/api/cron/*` accordingly.

## Cross-cutting UI/infra fixes (2026-09-04)

- **`TimeInput` component** (`components/ui/time-input.tsx`) replaced every native `<input type="time">` in the app (the weekly availability editor, both onboarding and club-settings Operating Hours steps, their `QuickSetupPanel`s). Reason: native time inputs on Windows Chrome ignore the page's `lang` attribute and instead follow the OS's regional format setting, which could silently show/accept a 12h AM/PM format instead of the 24h format the rest of the app assumes.
- **`BouncingBall` loader rollout** — the shared `components/BouncingBall/` spinner is now used consistently across loading states that previously had ad hoc spinners/skeletons, including `ClubOperationalGate`'s loading branch, `DashboardLoader`, `GlobalLoadingOverlay`, `CourtAvailabilityGrid`, the payment-return view, and the `CourtFormSheet` photo field.
- **`DashboardShell.tsx` build fix** — wrapped its `useSearchParams()`-consuming content in `<Suspense>` (`DashboardShell` now just renders `<Suspense fallback={<DashboardLoader />}><DashboardShellContent /></Suspense>`). Without it, `next build` failed to statically prerender any dashboard route with no other dynamic dependency (e.g. `/dashboard/browse/payment-return`) — see the Next.js "missing-suspense-with-csr-bailout" bailout rule.
